# 2026-06-16 Open Pulse Workshop

## Context

SDSC and Open Science Office (EPFL) led workshop, where researchers, software engineers came together to discuss the Open Pulse technicalities and important metrics. 

## Most Prevalent Metrics

CHAOSS:

- Activity Dates and Time ( most recent change + how long has the code been around --> There are probably better CHAOSS metrics targeting these)
- Community Activity Metric Model from CHAOSS
- Contributors
- Contributor Absence Factor
- License Coverage + SPDX
- Number of Downloads
- Release Frequency (good frequency defined by project type -- to be defined)
- Time to First Response (depends on project type - but allows someone new to the community to have an idea of if they answer slow or fast)

Other metrics not covered by CHAOSS:
- Activity metric (combining Contributor Absence Factor + others) => Goal is to have a barometer of activity (between red -inactive and green - active). A first high level entry point before seeing further
- [Check if there is equivalent in CHAOSS] Community Build metric: Are there focus groups, are there forum announcements
- Give back development loop metric: Technical Fork + New Contributors + PRs combined and centralized around the github username. This allows to see if someone forked, deved and then gave back as a new contributor via a PR.
- Multi domain metric: is the tool spanning multiple domains (biomedical, environmental, etc.)
- Stability + Interest metric = CAF + Organizational Project Skill Demand (Job adds) + Release Frequency assess stability and interest in project. 

## 3 User Personas Identified

3 Personas:

- Decision maker
- Researcher
- Developers

### Researchers

Concerns:

- Reusability
- Promote Career in Open source
- Does the code cover the theory ? 

Metrics:
- Activity metric
- Academic Open Source Project Impact
- Documentation Discoverability + Documentation Quality (see ENAC days)
- License Coverage + SPDX
- Number of Downloads
- Test Coverage
- Time to First Response (slow is acceptable)
- Qualitative theory metric: is the software cited in enough papers? For complex fields, are we sure the code implements the theory correctly?

Note: Contributors, Contributor Absence Factor do not matter for Research software where a single matainer can still provide a tool widely used.

### Developers

Example: SCALA

Concerns:

- Grants: Critical infrastructure. Show embedding in different spheres (academic, industry, etc.), for different organizations, different domains
- Decision making for dependencies: if a tool is active, maintained then ok to depend on it

Metrics:

- Activity metric
- Community Build metric
- Contributors
- Contrubutor Absence Factor
- Give back development loop metric
- License Coverage + SPDX
- Multi domain metric
- Number of Downloads
- Release Frequency (good frequency defined by project type -- to be defined)
- Stability + Interest metric
- Time to First Response (faster is better for dev)

## Different types of projects

Early stage projects will not have community indicators. 

Mature stage projects will have community indicators and then they can assess community health. 

Different kind of projects:

- Community tool (like SCALA)
- Research software

## Potential Community Use-Cases

Dashboards:

- ENAC GitHub organization - They are interested as to how repos and issues are spread around. They want visibility outside of EPFL community. They want to improve the way they do open source.
- SCALA: They have 2 Github orgs and more satellite projects. They want to have and be able to share an overview. They prefer too large view that you prune down than too small overview.
- CERN: They are working on an overview for a catalog of tools. They are bringing together CHAOSS and other sources / metrics for measuring code quality. They would be interested in the Open Pulse overview of the catalog.
